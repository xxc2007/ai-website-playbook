# Incident Case Library（故障案例库）

> 每条案例：现象 → 根因 → 定位 → 修复 → 防回归。均来自一个真实生产站点（单 VPS、TypeScript monorepo + PostgreSQL + systemd + nginx、`BASE_PATH` 子路径部署），已匿名化。排查通用顺序：先确认「线上跑的是不是刚发布的代码」（读 `.release` + `/api/health`），再查配置覆盖链，再查资源与锁。

## 1. 整站 404 —— BASE_PATH 丢失

- **现象**：全站路径 404，或页面能开但静态资源 404。
- **根因**：`BASE_PATH` 是**构建期变量**；只在运行环境改了环境变量、或上传了没带该变量构建的前端产物。
- **定位**：对比构建机环境与产物内路径前缀；`curl` 任一静态资源看实际路径。
- **修复**：带 `BASE_PATH=/app` 重新构建并重发布。
- **防回归**：构建命令与部署脚本写死同一变量来源；verify-deploy 加一条产物路径前缀检查。

## 2. 页面 200 但跑旧码 —— 半重启 / 漏单元

- **现象**：新功能没生效、旧 bug 还在，但发布流程显示成功。
- **根因**：只重启了部分常驻单元（如 web 重了、api 没重），或某节点角色化跳过逻辑没按预期生效。
- **定位**：逐台读 `.release` 完整 40 位 SHA + `systemctl show <unit> --property=ExecMainStartTimestamp` 对时间线。
- **修复**：补重启漏掉的单元；核对部署脚本的单元清单与角色跳过分支。
- **防回归**：验收必含「逐台 `.release` + 每单元重启时间戳」，不用 Git HEAD 代替。

## 3. 部署闸门误伤 —— 窗口文件残留

- **现象**：部署脚本直接拒绝执行，报「已有部署在进行」。
- **根因**：上一轮异常退出留下窗口/锁文件；或别的工作流持锁。
- **定位**：读窗口/锁文件内容（owner 与时间戳）；核对 `systemctl` 时间线判断是否真有并发部署。
- **修复**：仅当确认 owner 已结束且系统排空后，由人手工移除；**禁止**按时间、SSH 断连、PID 消失、数据库无连接推断排空并删锁。
- **防回归**：锁文件内容记录 owner/会话/时间；部署脚本收尾 finally 清理；拿锁用 `O_CREAT|O_EXCL`。

## 4. NAT 静默死链 —— keep_alive

- **现象**：某条内网穿透/代理链路平时正常，空闲一段时间后第一次请求超时或连接重置。
- **根因**：NAT 映射在空闲期被回收，无 keepalive 心跳。
- **定位**：复现「空闲 → 首请求失败 → 第二次成功」模式；对比两端连接表。
- **修复**：链路层加 keep_alive 心跳（应用层 ping 或 TCP keepalive 参数）。
- **防回归**：监控把「链路静默时长」作为指标；部署验收对该链路先打一发探测。

## 5. IO 饥饿导致假红验收

- **现象**：验收脚本全绿但个别读接口偶发超时；或反之——验收判红，但逐条核对全是「既有漂移」，本轮改动无辜。
- **根因**：慢盘高负载窗口（PSI `io full avg60` 接近/超过 40）放大了所有 IO 敏感操作；verify 的判红项可能是既有的配置漂移而非本轮回归。
- **定位**：`cat /proc/pressure/io` 看窗口内压力；对 verify 判红项做「两棵树 diff 零变化」核对，区分本轮回归与既有漂移。
- **修复**：既有漂移单独立项处置；本轮验收在压力回落后复跑。
- **防回归**：验收记录 PSI 采样；verify 脚本输出区分「新增判红」与「既有漂移」。

## 6. 连接池被 systemd EnvironmentFile 覆盖压成 2（读者面卡死）

- **现象**：聚合总览刷新不出来、点任意日期卡很久；`/api/health` 连续 `query_timeout`；某后台页 40 秒才出。
- **根因**：应用读侧按 `DATABASE_POOL_MAX` 建池，但 systemd drop-in 的 `EnvironmentFile /etc/<app>/pools.env` 里旧值 `DATABASE_POOL_MAX=2` **覆盖**了 `.env` 的期望值——读者面 4 个聚合槽抢 2 条连接全在排队。
- **定位**：读代码确认读的是环境变量 → `systemctl cat <app>-api` 看 drop-in 与 EnvironmentFile → `sudo tr '\0' '\n' < /proc/<MainPID>/environ` 读进程实际环境 → 文件 mtime 与 `ExecMainStartTimestamp` 对时间线 → journal 里的重启退出记录。
- **修复**：改 `/etc/<app>/pools.env`（数据库池 ≥8、队列池 ≥3）→ 重启 → **再读 `/proc/<pid>/environ` 验收**。
- **防回归**：配置验收口径 = 进程环境而非文件；部署脚本收尾打印关键池参数的实际生效值。

## 7. 用量总览 10 秒级全表聚合 + 57014 + 静默失败（诊断缺口）

- **现象**：后台总览永远停在「正在生成统计」；journal 里该功能日志恒为 0，但同日 `57014`（statement timeout）出现 19 次。
- **根因**：总览快照是无时间下界的 `GROUPING SETS` 全表聚合（Seq Scan 48.8 万 + 38.9 万行，空载 10.1 秒），压力下超 30 秒 `statement_timeout`；且**刷新失败分支只设 30 秒冷却、不打日志**——服务端零痕迹。
- **定位**：用应用同款会话设置（READ ONLY / statement_timeout 35s / work_mem 16MB / jit off / enable_sort off）`EXPLAIN ANALYZE` 复现；`pg_class.reltuples` 对表规模；journal 里 `grep -c 57014` 与该功能 grep 计数为 0 的反差即静默点。
- **修复**：止血 = 快照 `freshMs` 30s→300s + 失败分支补结构化 warn（含 code）+ 读接口 stale fallback（`canUseStale` 含 `57014`/`55P03`）；根治 = 加时间下界走部分索引，或建按天×模型×服务×计费类型的预聚合派生表。
- **防回归**：审查每个快照 reader 的失败分支必须有日志；测试环境注入一次超时，断言 journal 出现该 warn。

## 8. nav-counts 1 秒截止偶发 500 —— 缺 stale fallback

- **现象**：重聚合运行期间，后台布局角标偶发 500（journal：`GET /api/admin/nav-counts status=500 ... canceling statement due to statement timeout`）。
- **根因**：角标接口有 10 秒进程内缓存但**没配 stale fallback**：缓存过期后一次刷新超时（1 秒截止）就直接 500。
- **定位**：journal 500 时间点与重聚合快照落盘时间相关；读缓存封装确认 staleIfError 机制存在但调用方没传参。
- **修复**：补第三参 `{staleIfErrorMs: 600_000, canUseStale: e => ['57014','55P03'].includes(e?.code ?? ''), markStale: v => v}`——超时变成「先给上次角标值、后台重算」。
- **防回归**：所有带截止时间的读接口逐一核对是否接了 stale fallback；重聚合窗口内后台页面不再出 500（验收判据）。

## 9. 派生表回填直写不传播 + 外键索引缺失放大写入

- **现象**（口径错误）：标签回填脚本补进的数在统计页的 service/purpose 分组里不出现、`missing` 计数恒报。（性能错误）：标签写入后统计管道吞吐崩塌、回填脚本每批 5 秒超时。
- **根因**：同一事实表有两条写路径——上游触发器 upsert 与回填脚本直插；传播触发器只建在上游表上，覆盖不了直插路径（service 永久 NULL）。同时反向 UPDATE（按外键回填派生行）的表**没有外键索引**，每次上游写入对几十万行做同步 Seq Scan。
- **定位**：读两条写路径代码 + grep 全部迁移确认索引面（唯一索引是 `started_at` 部分索引，对按外键的 UPDATE 无用）；`EXPLAIN` 直插路径看 Seq Scan。
- **修复**：传播触发器改建在**派生表本体**（`AFTER INSERT OR UPDATE ON 派生表`，单触发器收口全部写路径）；同时建外键索引（迁移单事务内 `CONCURRENTLY` 不可用，普通构建锁写表分钟级，低流量窗口执行并如实声明）；大回填保持独立分批脚本（游标续跑、每批 `statement_timeout='5s'`、`lock_timeout='250ms'`）。
- **防回归**：回归测试覆盖两条写路径（标签先到 / 直插补录 / 删后重插 / 值未变 upsert 幂等四断言）；`EXPLAIN` 确认按外键的 UPDATE 走索引。

## 10. CI 时序敏感测试抖动 —— 锁观察 5 秒窗

- **现象**：必需检查的 Backend tests 间歇性失败，报 `Source wait not observed`；同一树哈希一次绿一次红，昨日同测试也这样失败过。
- **根因**：测试先 `FOR UPDATE` 加锁，再发起并发 upsert，随后 5 秒 deadline 内轮询 `pg_stat_activity` 观察锁等待——CI 负载下 5 秒不够；且谓词依赖查询文本匹配（`query LIKE '%FOR KEY SHARE%'`）不稳。
- **定位**：`gh run view <run-id> --log-failed` 读报错原文；对比「同树 PR run 全绿 + 同 run docker job 成功」排除内容回归。
- **修复**：先 `gh run rerun <run-id> --failed`；仍红则放宽 deadline（5s→15s）、谓词换成确定性阻塞判定（`pg_blocking_pids(pid)` 非空 + 同库非自身连接）、超时附 `pg_stat_activity` 快照，按 PR 合并。
- **防回归**：并发观察测试统一用确定性谓词模板；超时输出带上现场快照。

## 11. 部署脚本自身 bug —— 首次 apply 失败，DRY-RUN 覆盖不到

- **现象**：DRY-RUN 通过，首次 `--apply` 在远端中途死掉，报脚本变量未定义。
- **根因**：`--apply` 分支引用了只在另一分支定义的 shell 变量；DRY-RUN 路径没走到这行。
- **定位**：读部署日志定位失败行号 → 对照脚本该行 → 确认变量定义分支。
- **修复**：修脚本发 PR（脚本也是代码，走同流程）→ 重跑。
- **防回归**：DRY-RUN 尽量走与 apply 相同的代码路径（只把「改状态」的操作替换成打印）；上线前对脚本做 shellcheck。

## 12. SSH 连发停滞 —— banner 超时

- **现象**：部署上传阶段连发 SSH 时，连接卡在 banner exchange 超时（~120 秒），直连与堡垒链路都触发。
- **根因**：服务器 `MaxStartups 10:30:100` + fail2ban 在持续扫描噪声下（实测数万次失败/数百封禁）把合法连发也挡住。
- **定位**：`sudo ss -tnp` 看连接状态；journal 里 sshd banner 超时计数；fail2ban 封禁数。
- **修复**：本轮以护栏重试循环 + 低频直连路线完成部署；服务器侧整改（调 `MaxStartups`、fail2ban 白名单）单独立项与 owner 确认。
- **防回归**：部署脚本内置重试护栏（指数退避 + 上限）；上传改单连接复用（`scp -O` / `rsync` 或 ControlMaster）。

## 13. .env 备份放在代码目录 —— 漂移

- **现象**：verify-deploy 判红，报 `.env.bak-*` 出现在应用代码目录。
- **根因**：手工操作图省事把 env 备份落进了代码目录，违反「备份与 `.env` 放 `$APP_HOME`，不进代码目录」的规约。
- **定位**：verify-deploy 的漂移清单；`ls /opt/<app>/app/.env*`。
- **修复**：`mv` 到 `/opt/<app>/`（移动也属逐条确认项，不是随手清）。
- **防回归**：verify-deploy 固化该检查项；部署脚本的备份路径集中定义。

## 14. 角色化 disabled 单元被误判为可清理

- **现象**：盘点发现节点上十几个 disabled 单元（备用网关、分时段 timer 等），直觉列为「无效资产」候选。
- **根因**：disabled 单元是**按角色休眠**的设计（如 readers-only 节点保留 worker 定义但不启用），与安装脚本的 ALL_UNITS 注释一致——不是无效资产。
- **定位**：对照安装脚本的单元清单与角色注释；`systemctl cat <unit>` 看描述。
- **修复**：不清理；盘点文档标注「角色化休眠，勿清理」。
- **防回归**：清理候选判定必须对照单元角色定义，不单看 enabled 状态。

## 15. 每日期独立快照首开慢 + 生成态轮询观感

- **现象**：日历上点任一过去日期，首次都要等几秒，页面先显示「正在生成统计」轮询。
- **根因**：快照键含日期、盘上缓存 24 小时过期 → 每个日期每天首开现场跑 SQL；日期过滤能走部分索引，但 `LEFT JOIN` 标签表整表 Seq Scan（实测 1.9 秒）；前端生成态 5 秒轮询拉长观感。
- **定位**：`EXPLAIN ANALYZE` 日期变体（Bitmap Index Scan 命中但 join 侧整表读）；服务器快照目录按落盘文件对号键摘要。
- **修复**：join 改为预限子查询（先按当天窗口限定 receipt 集合再 join），日期快照重建降到亚秒；根治同 §7 派生表方案。
- **防回归**：验收判据「连点 5 个不同日期无一次卡 >5s」；快照落盘耗时基线记录。

## 16. 快照 version bump 后冷启动重建

- **现象**：口径修复发版后，首次打开统计页短暂回到「正在生成统计」。
- **根因**：快照存储版本串 bump 后，盘上旧快照全部过期，首次访问触发重建；重建受资源余量闸门影响可能偏慢。
- **定位**：读快照存储的 version 与过期逻辑；服务器快照目录确认旧文件不再命中。
- **修复**：预期内一次性代价，选低流量窗口部署；启动预热任务（prime 脚本）缓解。
- **防回归**：bump 版本串时在 PR 描述声明冷启动重建代价；部署后观测窗口内确认 generating 态消失而非长期停留。

## 17. 同机备份单元 failed —— 非本站资产也要上报

- **现象**：`systemctl --failed` 列出同机另一站点（个人/纪念册站）的备份单元 failed。
- **根因**：备份中断（存储端或脚本问题），与本站无关但同机共担风险。
- **定位**：`systemctl status <unit>`、`journalctl -u <unit>`。
- **修复**：上报 owner 处理；只读会话不动它。
- **防回归**：运维巡检口径包含 `systemctl --failed` 全列表，不筛只看自己的单元。

## 18. 「引用既有契约」未证实 —— 空实现陷阱

- **现象**：方案引用「既有提示路径」（前端据某字段显示回填中提示），实现时发现该路径从未存在：相关 if 块是空的、字段在返回前被剥除、前端 grep 零命中。
- **根因**：注释里写了「前端可据此显示提示」，被当成了已实现的功能。
- **定位**：grep 前后端全字段名 + 读相关代码块；测试对照真实契约（只保证「不阻断读」那一半）。
- **修复**：按真实存在的契约改写方案；未实现的提示如需要，单独立 PR，不顺手扩面。
- **防回归**：引用「既有契约」前必须 grep 证实实现存在——**注释不等于功能**。
